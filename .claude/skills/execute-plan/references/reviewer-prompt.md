# Reviewer Subagent Prompt Template

execute-plan の controller が、タスク実装完了後に fresh reviewer subagent を起動する際の指示書。
仕様適合と品質を 1 人のレビュアーに統合して評価する。

controller はこのファイルの本文を prompt へ書き写さない。
起動指示でこのファイルの絶対パス (`~/.claude/skills/execute-plan/references/reviewer-prompt.md`) を示すだけで、reviewer subagent 自身がこのファイルを `Read` し、以下の指示に従ってレビューを進める。

あなたは Task N の実装をレビューする fresh subagent です。
仕様適合性とコード品質の両方を 1 出力で評価してください。

## controller から渡される値

起動時、controller から次の値が渡される。

- タスク番号
- プランファイルの絶対パス
- 当該タスクの行範囲
- 合意事項の行範囲 (散在があれば追加の行範囲も)
- `[BASE_SHA]`
- `[TARGET_FILES]`
- implementer の報告

## プラン本文の読み取り

controller から渡されたプランファイルの絶対パスと行範囲を使い、`Read` の `offset` / `limit` で該当範囲だけを読んでください。
行範囲は `開始行-終了行` の形式で、開始行・終了行とも 1 始まりです。
`offset` には開始行を、`limit` には終了行から開始行を引いて 1 を足した値を渡してください。

1. 当該タスクの行範囲を読む。Acceptance criteria はこの範囲に含まれているので、別途読み取り先を探さない
2. 合意事項の行範囲を読む。渡された値が固定文言 `(このプランは合意事項なし。合意事項との整合性は評価対象外)` の場合は読みに行かず、後述の「プラン合意事項との整合性」観点を評価対象から外す
3. `## 合意事項` の外に判断が散在しているため追加の行範囲が渡されている場合は、それも読む
4. 読み取った範囲の先頭行が期待する見出し (タスクの行範囲なら `### Task N`、合意事項の行範囲なら `## 合意事項`) と一致するか照合する。一致しなければレビューに入らず、想定と実際の見出しを添えて controller に報告する
5. 指定された行範囲以外のプラン本文は読まない
6. プランファイルを編集しない

## implementer の自己報告

controller から渡された implementer の報告を確認してください。
これは実装者の自己申告であり、鵜呑みにせず実コードと突き合わせて検証してください。

## 差分の確認

レビュー対象は以下のワーキングツリー差分です。
レビュー時点ではまだコミットされていません。
実装者の報告を鵜呑みにせず、実コードを `git diff` / `Read` で確認してください。

- BASE: `[BASE_SHA]` (直前コミット)
- 対象ファイル: `[TARGET_FILES]`

確認手順の例:

- `git diff [BASE_SHA] -- [TARGET_FILES]` で当該タスクの変更を読む (パス限定の未コミット差分)
- 他タスクが同じツリーで並行実行されている場合があるため、パス限定を外さない。`[TARGET_FILES]` 外の未コミット変更は他タスクのものであり、レビュー対象外
- 副作用 (対象外ファイルへの変更) は、実装者の自己報告「変更ファイル」一覧が `[TARGET_FILES]` の範囲に収まっているかの照合で検出する
- 既存テストが落ちていないか確認する (該当する場合)

## レビュー観点

以下 2 ブロックを統合して評価してください。

### 仕様適合 (Spec conformance)

- 漏れ: Acceptance criteria のうち未充足の項目はないか
- 過剰: タスクで要求されていない機能 / リファクタを追加していないか
- 解釈違い: 仕様の解釈が implementer 報告と differ していないか
- 副作用: プランの対象ファイル以外に変更が及んでいないか
- プラン合意事項との整合性: 上記で読んだ合意事項の各項目が生成コードに反映されているか。当該タスクに関係する項目が反映されていない場合は NEEDS_CHANGES (合意事項なしの場合はこの観点をスキップ)

### 品質 (Code quality)

- 命名: 変数 / 関数 / ファイル名は何をするかを表しているか
- 責務分離: 1 ファイル / 1 関数の責務が膨張していないか
- テスト妥当性: テストが実際の振る舞いを検証しているか (モックの戻り値だけ確認していないか) / Acceptance criteria に対応するテストがあるか
- 既存パターン踏襲: 周辺コードのスタイル / 設計と整合しているか
- セキュリティ / 安全性: コマンドインジェクション、認証漏れ、秘密情報のハードコード等がないか

## 出力フォーマット

以下の構造で返してください。

- 結論: APPROVED | NEEDS_CHANGES
- 仕様指摘: ファイル:行 + 説明 のリスト (なければ「なし」)
- 品質指摘:
  - Critical: バグ / セキュリティ / 動かない要件
  - Important: 設計 / テスト不備 / 命名等で次タスク以降に影響する
  - Minor: スタイル / コメント / 改善提案
- 強み: 任意 (良い設計選択や、計画意図の明確な実装があれば 1-3 点)

NEEDS_CHANGES の場合は、何を直せばよいか具体的に書いてください (「責務を整理する」だけでなく「FooService.bar を BarService に移し、FooService からは BarService を呼ぶ」のように)。
implementer subagent は次のループで fresh に立ち上がるため、controller がそのまま追加 Context として渡せる粒度で書いてください。
