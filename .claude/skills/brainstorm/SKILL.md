# Brainstorm

機能追加・実装方針・技術的な設計の要件を、進行プロトコルに従って固めていくスキル。ゴールはアドリブ議論による品質のばらつきをなくし、確定した判断を設計メモとして残し、write-plan にそのまま引き継げる状態にすることにある。事業アイデア・サービス案・新規事業提案の評価は扱わない(business-idea-review の対象)。

## Current state

- 既存メモ: !`ls docs/workflow/memo/ 2>/dev/null || echo '(none)'`
- Today: !`date +%Y-%m-%d`

## 進行プロトコル

1. 検討対象と背景を確認する。何のための検討か(機能追加 / 実装方針 / 設計判断)、関連する既存コード・ドキュメントがあれば `Read` / `Glob` / `Grep` で把握する。曖昧なら検討対象をユーザーに確認してから進む。
2. 論点を 1 つずつ扱う。検討すべき論点を洗い出し、1 論点ずつ深掘りする。複数論点を同時に投げない。ある論点が確定してから次の論点に移る。
3. 選択肢は 2〜4 個で提示する。各論点についてアプローチ案を 2〜4 個に絞り、メリット・デメリット・実装コストを添えた比較をチャット本文に書く。`AskUserQuestion` は選択を取るためだけに呼び、比較を選択肢のフィールドに押し込まない(書き方は下記「AskUserQuestion の書き方」)。絞り込んでも多すぎる場合は判断基準から確認する。
4. YAGNI を必ず 1 回問う。検討の中で「これはどこまで小さくできるか」を、`AskUserQuestion` で少なくとも 1 回ユーザーに問う。過剰設計を避けるための固定ステップで、省略しない。
5. `AskUserQuestion` でユーザーの選択を得て論点を確定する。棄却した選択肢は設計メモにもプランにも書かない(比較の記録はここで手放してよい。今回扱わないと決めた対象は、棄却案とは区別して出口の設計メモ「スコープ外にしたもの」に残す)。

## AskUserQuestion の書き方

brainstorm 内の全ての `AskUserQuestion` 呼び出しに適用する。

### 何を聞くか

- ユーザーが答えを持っている問いだけを聞く。実装の細部やこちらで決められることは聞かず、自分で決めて結果を報告する
- 比較(メリット・デメリット・実装コスト)はチャット本文に書き、`AskUserQuestion` は選択を取るためだけに呼ぶ
- チャット本文には案どうしを並べた比較を書き、`description` にはその案単体の要約を書く

### 各フィールドの書き方

- `question`: チャット本文を読まなくても単独で意味が通る完全な文にする。「これ」「それ」だけで対象を指さない
- `label`: 選択肢の中身を表す日本語の名詞句にする。スキーマの "1-5 words" を日本語の語数制限として読まない
- `description`: 1〜2 文で、選ぶとどうなるかと主な短所 1 つを書く
- `header`: 表示幅が狭いので短く保つ

`question` と `description`、およびチャット本文の比較は、output style の「既定は短く」の対象外とする。
ここを削ると質問の意味が取れなくなり、ユーザーが「何を聞いているのか」を問い直すことになる。

### 使ってはいけない表現

- 定型文の反復: 「代わりに、〜ます」のような同じ構文を全選択肢で機械的に繰り返さない
- 中身の無い短所: 「線引きは曖昧なまま残ります」のように、選んだ結果何が起きるか分からない抽象語を書かない
- 造語・耳慣れない語: 「地の文」のように、ユーザーが使っていない語を持ち込まない
- 英語からの直訳: 「一覧で行を拾う」のように、日本語として何を指すか伝わらない訳語を書かない

### 例

以下は書き方の見本であり、brainstorm への指示ではない。
同じ 1 つの質問を、悪い書き方と良い書き方で並べてある。

悪い書き方。

```text
question: ログの扱いはどうしますか。
header: ログ
label: 一覧で行を拾う
description: 一覧から必要な行だけを取得します。代わりに、実装が増えます。
label: 全部読む
description: 全件を読み込みます。代わりに、メモリを使います。
```

良い書き方。比較をチャット本文に置き、選択肢には各案の要約だけを置く。

```text
[チャット本文]
ログの読み込み方は 2 案あります。
1 行ずつ読む方式は 100 万行でもメモリを一定に保てますが、中断したときの再開位置を自前で記録する必要があります。
全件を一度に読む方式は実装が 10 行ほどで済みますが、ログのサイズと同じだけメモリを使います。
現状のログは最大 200 MB です。

[質問]
question: ログファイルの読み込み方式を、どちらにしますか。
header: 読み込み方式
label: 1 行ずつ読む
description: メモリ使用量がログのサイズに依らず一定になります。中断したときの再開位置を自前で記録する必要があります。
label: 全件を一度に読む
description: 実装が 10 行ほどで済み、既存の処理をそのまま使えます。200 MB のログでメモリを 200 MB 使います。
```

## 出口: 設計メモの作成

全論点が確定したら、以下の手順で設計メモを作成して検討を終える。

1. `docs/workflow/memo/` が無ければ作成する。

   ```bash
   mkdir -p docs/workflow/memo
   ```

2. topic(内容を表す短い kebab-case)を決め、`docs/workflow/memo/YYYY-MM-DD-<topic>.md` として `Write` する(`YYYY-MM-DD` は Current state の Today)。
3. 次の 3 部構成で書く。

   ```markdown
   # <topic>

   ## 目的

   <なぜこの検討をしたか、何を達成したいか>

   ## 確定判断とその根拠

   1. <決めたこと 1〜2 行> — 根拠: <その判断を選ばせた制約・理由 1 行>
   2. ...

   ## スコープ外にしたもの

   - <今回は扱わないと決めたもの>
   ```

   「確定判断とその根拠」は、write-plan が `## 合意事項` へそのまま転記できる粒度(1 判断につき「判断 1〜2 行 + 根拠 1 行」)で書く。
4. 「スコープ外にしたもの」は設計メモに一覧として残す。そのうち後から着手しうるものを、`Skill` ツールで issue-tracker を起動して create モードで起票する (起票する旨と件数を先に伝えてから起動する)。粒度は次の通り。
   - 1 項目 = 1 issue を既定とする。issue-tracker は 1 issue = 1 ファイルで triage するため、独立して着手できる単位で分けないと棚卸しで扱えない
   - ただし、同じ変更でまとめて片付く項目 (同一ファイル・同一機能の派生など、片方だけ着手する意味がないもの) は 1 issue にまとめる
   - 一覧が「今回は考えないと決めた」だけで着手対象になりえない項目のみなら、起票せず設計メモの記載で終える
5. 保存パスを報告し、write-plan へ引き継ぐ旨を伝えて終了する。

## write-plan への接続

- 設計メモの「確定判断とその根拠」が、write-plan が合意事項ありのプランを書く際の `## 合意事項` の転記元になる。判断はこの設計メモの時点で確定させ、プラン段階で議論を再開しない。
- 合意事項の要否の判定は write-plan 側が行う。brainstorm はここに関与しない。

## write-plan からの差し戻し

write-plan の執筆中に合意事項相当の新たな設計判断が必要になった場合、「何が未確定か」を 1 行添えて brainstorm へ差し戻される。差し戻しを受けたら次の手順で対応する。

1. 差し戻された論点について、進行プロトコルに従って検討を再開する(論点を 1 つずつ、選択肢 2〜4 個。YAGNI は初回検討で既に問うていれば再度問う必要はない)。
2. 確定した判断を、既存の設計メモの「確定判断とその根拠」に追記する(新規ファイルは作らない。対象メモは Current state の既存メモ一覧、または差し戻し元から示されたパスで特定する)。
3. 追記したパスを示し、write-plan へ戻す旨を報告して終了する。
