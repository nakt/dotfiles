# Brainstorm

機能追加・実装方針・技術的な設計の要件を、進行プロトコルに従って固めていくスキル。ゴールはアドリブ議論による品質のばらつきをなくし、確定した判断を設計メモとして残し、write-plan にそのまま引き継げる状態にすることにある。事業アイデア・サービス案・新規事業提案の評価は扱わない(business-idea-review の対象)。

## Current state

- 既存メモ: !`ls docs/workflow/memo/ 2>/dev/null || echo '(none)'`
- Today: !`date +%Y-%m-%d`

## 進行プロトコル

1. 検討対象と背景を確認する。何のための検討か(機能追加 / 実装方針 / 設計判断)、関連する既存コード・ドキュメントがあれば `Read` / `Glob` / `Grep` で把握する。曖昧なら検討対象をユーザーに確認してから進む。
2. 論点を 1 つずつ扱う。検討すべき論点を洗い出し、1 論点ずつ深掘りする。複数論点を同時に投げない。ある論点が確定してから次の論点に移る。
3. 選択肢は 2〜4 個で提示する。各論点についてアプローチ案を 2〜4 個に絞り、メリット・デメリット・実装コストを添えて比較提示する。
4. YAGNI を必ず 1 回問う。検討の中で「これはどこまで小さくできるか」を、`AskUserQuestion` で少なくとも 1 回ユーザーに問う。過剰設計を避けるための固定ステップで、省略しない。
5. `AskUserQuestion` でユーザーの選択を得て論点を確定する。棄却した選択肢は設計メモにもプランにも書かない(比較の記録はここで手放してよい。今回扱わないと決めた対象は、棄却案とは区別して出口の設計メモ「スコープ外にしたもの」に残す)。

## 出口: 設計メモの作成

全論点が確定したら、以下の手順で設計メモを作成して検討を終える。

1. `docs/workflow/memo/` が無ければ作成する。

   ```bash
   mkdir -p docs/workflow/memo
   ```

2. topic(内容を表す短い kebab-case)を決め、`docs/workflow/memo/YYYY-MM-DD-<topic>.md` として `Write` する(`YYYY-MM-DD` は Current state の Today)。
3. 次の 3 部構成で書く。

   ```markdown
   # <topic>

   ## 目的

   <なぜこの検討をしたか、何を達成したいか>

   ## 確定判断とその根拠

   1. <決めたこと 1〜2 行> — 根拠: <その判断を選ばせた制約・理由 1 行>
   2. ...

   ## スコープ外にしたもの

   - <今回は扱わないと決めたもの>
   ```

   「確定判断とその根拠」は、write-plan が `## 合意事項` へそのまま転記できる粒度(1 判断につき「判断 1〜2 行 + 根拠 1 行」)で書く。
4. 「スコープ外にしたもの」は issue-tracker に起票しない。記録先はこの設計メモと PR 本文に限る。
5. 保存パスを報告し、write-plan へ引き継ぐ旨を伝えて終了する。

## write-plan への接続

- 設計メモの「確定判断とその根拠」が、write-plan がフル形プランを書く際の `## 合意事項` の転記元になる。判断はこの設計メモの時点で確定させ、プラン段階で議論を再開しない。
- 規模判定(短縮形 / フル形の選択)は write-plan 側が行う。brainstorm はここに関与しない。

## write-plan からの差し戻し

write-plan の執筆中に合意事項相当の新たな設計判断が必要になった場合、「何が未確定か」を 1 行添えて brainstorm へ差し戻される。差し戻しを受けたら次の手順で対応する。

1. 差し戻された論点について、進行プロトコルに従って検討を再開する(論点を 1 つずつ、選択肢 2〜4 個。YAGNI は初回検討で既に問うていれば再度問う必要はない)。
2. 確定した判断を、既存の設計メモの「確定判断とその根拠」に追記する(新規ファイルは作らない。対象メモは Current state の既存メモ一覧、または差し戻し元から示されたパスで特定する)。
3. 追記したパスを示し、write-plan へ戻す旨を報告して終了する。

## Key Principles

1. 論点は 1 つずつ扱う。並行して複数論点を投げない。
2. 選択肢は 2〜4 個に絞る。多すぎる場合は判断基準から確認する。
3. 「これはどこまで小さくできるか」は検討中に必ず 1 回問う。
4. 棄却した選択肢・比較過程は記録しない。残すのは確定判断とその根拠のみ。
5. スコープ外にしたものの記録先は設計メモと PR 本文。issue-tracker には起票しない。
6. 確定した判断はこの段階で固める。プラン段階(write-plan)で議論を再開しない。
7. Markdown スタイルは `~/.claude/rules/markdown-style.md` に従う。
