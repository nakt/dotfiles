# Plan Audit — 実装計画の反証監査

目的は承認ではなく反証の試行である。「この計画が失敗するとしたらどこか」を本気で探す。plan-reviewer(曖昧さ解消の対話型確認)とは役割が異なる。

## 憲章(絶対遵守)

LLM には提示された案に同調し、形だけの懸念を添えて承認する強い傾向がある。このスキルはそれを手続きで打ち消す。

- 「全体的には良くできています」型の総評を書かない。総評は判定と根拠のみ。
- 一般論の指摘をしない。指摘はすべて、この plan の具体的な記述・前提・文脈に紐づける。
- 採点(10 点満点等)をしない。
- [決定を覆しうる] がゼロ件なら、どの角度から反証を探し、何が反証にならなかったかを説明する義務を負う。
- 同じ会話で plan の作成に自分が関与していた場合、その旨を冒頭に明示し、別セッション/サブエージェントでの再レビューを推奨として記載する。

## 発動条件(正典はこの節。rules 側に複製しない)

以下のいずれかを含むプランに適用する。判定基準は行数や規模ではなく、不可逆性と影響範囲である。

- 新しい依存(ライブラリ・フレームワーク・外部サービス)の導入
- データスキーマ、永続化形式、API 互換性への影響
- 後から戻すコストが高い決定
- 複数モジュールを横断する構造変更
- 分析・分類・評価の手法選定

## 監査該当プランの追加要件

該当プランは、通常構成(要約 / 合意事項 / 実装タスク)に加えて以下を含むこと。通常プランにはこれらを要求しない。

- `## 前提と制約`: 既存資産・運用体制・データ量の想定・非機能要件
- 合意事項の各項目に、棄却した代替案 1 行

両方欠けている場合は監査を実施せず差し戻す(欠落を列挙し追記を求める)。1 つだけ欠けている場合は監査を実施しつつ、欠落自体を重大度付きの指摘として記録する。

## 監査の進め方 — 深掘り優先

観点メニュー(次節)から、この plan を最も殺しそうな角度を 2〜3 選び、深く掘る。冒頭で選んだ角度と、有力だが選ばなかった角度の理由を宣言する。網羅は目的ではない。指摘の数より、1 つの指摘の致命度と根拠の強さを優先する。

参照範囲(アンカリング防止): 監査の根拠は plan 本文のみとし、経緯・議論ログ・過去チャットは参照しない。plan に前提が書かれていないなら、それ自体を記載漏れとして指摘する。既存コード・スキーマの参照は、plan と実態の齟齬および既存構造との噛み合いの検証に限り可。作者の意図の推測には使わない。

## 観点メニュー

### 決め方

各決定に、この文脈(前提と制約)における根拠が紐づいているか。「一般的だから」は根拠ではない。棄却理由は事実として正しいか(古い情報・わら人形になっていないか)。不可逆な決定が安易に、可逆な決定が過剰に検討されていないか。

### 整合

処理を段に分解し、段間の入出力の型・形式・暗黙の前提(ソート済み・重複なし等)が噛み合うか。前段の失敗(欠損・分類不能・低信頼度)が後段でどう扱われるか。各段で捨てられるデータの合計が最終出力にどんな系統的偏りを作るか。再実行・冪等性。規模が 10 倍になったとき最初に破綻する段はどこか。評価スコアリング系(スコアリング→補正→集約→選別)では、補正の重ね掛けと選別が作る系統バイアスを重点的に見る。

### 手法(手法選定を含む plan では web 検索必須)

plan が解く問題を分野の標準用語に言い換える(例:「問い合わせをタグ階層に振り分ける」→ hierarchical text classification)。この一般名称で検索し、標準手法・既知の落とし穴・採用ツールのメンテナンス状況を確認する。より単純な手法(ルールベース・既存ライブラリ)で足りないかを必ず問う — 分析系で最も多い失敗は手法の過剰選定である。代替が見つからない場合は使用した検索クエリを列挙し、探索が不十分である可能性を明記する。決定に影響する事実主張(性能値・機能・互換性)は検索で裏を取り、取れなければ「未検証事項」に載せる。

### 設計(この 6 観点の正典はこの節)

既存コードを Grep 等で確認して判定する。

- 重複の作り込み: 新設する仕組みと同じ役割のものが既存にないか
- 特別扱いの累積: 追加する分岐は何個目か。3 個以上なら一般化が検討されたか
- 旧経路の残置: 置き換え時、旧経路の削除が計画に含まれるか(「後で消す」は削除計画ではない)
- 到達経路の欠落: 追加するものを誰が呼ぶか、実体として特定できるか
- 語彙の不統一: 導入する名前が既存の同じ概念と一致するか
- 拡張点の不在: 同種の変更が次に来たとき、触る箇所が増えていないか

## 出力形式

採点はしない。以下の構成を守る。

```text
# Plan Audit: [plan名]

## 判定
[このまま実装に進んでよい / 指摘事項を解消してから進む / 前提から再検討]
根拠: (決め手となった指摘を 1〜3 行)

## 選んだ角度
(深掘りした 2〜3 角度と、選ばなかった有力角度の理由。手法を選んだ場合は使用した検索クエリ)

## 指摘事項
### [重大度] 指摘タイトル
- 対象: plan のどの記述・決定か
- 内容: 何が問題か(この plan の文脈に即して)
- 根拠: なぜそう言えるか(検索を使った場合は出典)
- 提案: どうすればよいか

重大度: [決定を覆しうる] / [修正すべき] / [検討の余地]

## [決定を覆しうる] がゼロ件の場合の説明
どの角度から反証を探し、なぜ見つからなかったか。(1 件以上あれば省略)

## 未検証事項
裏を取れなかった plan 内の主張・前提
```

保存先: `.workspace/audits/<plan名>-audit-<YYYYMMDD>.md`。書き込みできない状況(plan モード・チャット環境)では会話内に出力する。
