# Write Plan

確定した判断と実装手順を 1 つのプランファイルに書き起こす。プランは実装者への唯一の引き渡し口であり、ここに無い判断は実装に渡らない。

## Current state

- Today: !`date +%Y-%m-%d`
- 設計メモ: !`ls docs/workflow/memo/ 2>/dev/null || echo '(none)'`

## 設計メモの取り込み

規模判定の前に、`brainstorm` の設計メモ (`docs/workflow/memo/YYYY-MM-DD-<topic>.md`) を確認する。今回のトピックに対応するメモがあれば、執筆前に `Read` で全文を読む。

- 対象メモの特定: 呼び出し元 (brainstorm や依頼文) からパスが示されていればそれを使う。示されていなければ Current state の設計メモ一覧から、トピックが一致するものを選ぶ。候補が複数あって決められないときは `AskUserQuestion` で確認する
- 該当メモが無い場合 (`(none)` を含む) はこの節を飛ばし、依頼文と既存コードを判定材料にする。メモが無いこと自体は差し戻し理由にしない
- 読んだメモの「確定判断とその根拠」は `## 合意事項` の転記元、「スコープ外にしたもの」はプランの対象範囲を絞る材料として使う。判断はメモの時点で確定済みなので、ここで議論を再開しない

## 規模判定

執筆に入る前に 1 回だけ判定する。判定材料は「設計判断・確定すべき合意事項が 1 つでもあるか」。設計メモを読んだ場合は、その「確定判断とその根拠」がそのまま判定材料になる。

- 無い (実装手順だけで決着する) → 短縮形: `## 要約` + `## 実装タスク`
- 有る → フル形: `## 要約` + `## 合意事項` + `## 実装タスク`

判定は執筆前の 1 回のみ。執筆の途中で形を選び直さない。

## 保存先

- スキル単独で起動された場合: `.claude/plans/YYYY-MM-DD-<topic>.md` (日付は Current state の Today、`<topic>` は内容を表す短い kebab-case)
- plan mode 中: ハーネスが指定するプランファイルを唯一のプランファイルとする (下記「プランファイルの運用」)

## プランの構成

以下のセクションのみ。この順序・見出し名で置く (短縮形では `## 合意事項` を置かない)。`## 実装タスク` は短縮形・フル形とも必ず置く。実装タスクを持たないプランは write-plan では生成しない (実装を伴わない調査・設計の記録は `brainstorm` の設計メモの領分)。

### ## 要約（必須）

5〜10 行で「何を・なぜ・どう変えるか」。略語・コードネーム・内部名称を使わない。ここだけ読めば承認判断ができることが基準。

### ## 合意事項（フル形で必須）

A1, A2… と番号付きで、1 判断につき「判断 1〜2 行 + 根拠 1 行」。根拠には、その判断を選ばせた制約（既存資産・データ量・運用体制・非機能要件など）を書く。AskUserQuestion で確定した判断も、代替案比較で選んだ判断も、このプラン内では合意事項に一元化する。棄却案・代替案の比較はプランに書かない。

execute-plan の controller はこのセクションを implementer / reviewer prompt に転記する。ここに無い判断は実装に引き渡されない。

### ## 実装タスク

実装者向けの本文。`### Task N: <短い動詞句のタスク名>` 見出しで 1 タスクを区切り、各タスクに次の 5 項目を書く。

- 目的: 1 文
- 対象ファイル: パスと区分 (新規 / 編集 / 削除)
- 依存: なし、または先行タスク名
- Acceptance criteria: 観測可能な完了条件をチェックボックスで
- Context: このタスクがどこに位置するか、周辺の前提、関連既存実装

各項目の具体的な書き方と、execute-plan の controller 側の抽出規則は `references/task-format.md` に従う。

## 未確定事項が出てきたとき

プランに未確定事項を持ち込まない。執筆中に合意事項相当の設計判断 (妥当な選択肢が複数あり、根拠を添えて確定する必要があるもの) が新たに出てきたら、その場で推測して埋めず、執筆を中断して要件検討 (`brainstorm` スキル) へ差し戻す。差し戻すときは、何が未確定かを 1 行で示す。

## 自己レビュー

書き終えたら以下を自分で確認し、引っ掛かったものはその場で直す。

- プレースホルダーの走査: 「TBD」「後で」「後で決める」「実装時に判断」等の記述が残っていないか。残っていれば埋める。埋められないなら上記「未確定事項が出てきたとき」の差し戻しに乗せる
- 受け入れ基準の検証可能性: 各 Acceptance criteria が観測可能・コードで確認できるか。「適切に」「きれいに」のような主観的表現がないか
- 要約が `## 要約` に定めた行数に収まるか。収まらないなら盛り込みすぎとみなし、決定のほうを落とす

タスクの粒度・独立性・依存の明示・Context の自己完結性は plan-reviewer の「execute-plan 適用性検査」が持つ観点なので、ここには複製しない。短縮形は plan-reviewer を呼ばないため、上記に加えて `~/.claude/agents/plan-reviewer.md` の当該節を `Read` し、そこに書かれた観点を自分で 1 回通す。フル形は下記「レビュー手順」の plan-reviewer 呼び出しで担保されるので、ここで二重に確認しない。

## レビュー手順（フル形のみ）

1. プランを作成したら plan-reviewer サブエージェントを呼び出す。プランのパスと作成中に読んだ主要関連ファイルのパス一覧を渡し、結論・経緯は渡さない。レビュー観点は plan-reviewer 定義（`~/.claude/agents/plan-reviewer.md`）が持つので、観点を prompt に書き足さない。
2. 結果をユーザーに確認する（原則 AskUserQuestion 1 回。4 問を超える場合は重要度順に分割）。
3. 確定事項をプランに反映して実装開始。再レビューはユーザーが明示的に求めたときのみ行う。

レビューの指摘は、反映する前に要約を書き直して確かめる。要約が `## 要約` に定めた行数に収まらなくなる、あるいは失敗経路や条件分岐の説明が要るようになったら反映せず、指摘が集中した決定のほうを落とす。実害: 指摘を順に取り込み、要約を書き直さないまま変更範囲が 2 ファイル 4 箇所から 6 箇所に膨れ、ユーザーの介入で差し戻した。

## プランファイルの運用

- plan mode 中は plan mode が指定するファイルを唯一のプランファイルとする。確定済みプランがある状態で plan mode に入ったら、冒頭の固定マーカー「このファイルは参照スタブ。実行対象: <本体プランのパス>」と要約数行だけの参照スタブを書いて承認に進む。スタブに `## 実装タスク` 見出しは置かない。実害: 同セッションで確定済みプランを plan mode 用に 5.7 分かけて再生成した。
- スタブは承認後も残す。承認直後に execute-plan が起動され、冒頭のマーカーを読んで本体プランへ読み替えるため、実装開始前に削除しない。インライン実装で進める場合だけ、読み替え先の本体プランのパスを明示してから着手する。
