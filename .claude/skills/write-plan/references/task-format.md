# 実装タスクの記述形式

`/execute-plan` で実装フェーズを進めるプランには `## 実装タスク` セクションを設け、各タスクを以下の構造で書く。
controller はこの形式を前提に、fresh subagent へプランファイルの絶対パスとタスク番号を渡す。
subagent は自分で `### Task N:` 見出しを探し、その範囲を読む。

````markdown
## 実装タスク

### Task 1: <短い動詞句のタスク名>

目的: <1 文>

対象ファイル:

- `path/to/file.ts` (新規 / 編集 / 削除)

依存: なし / Task 0 完了後

Acceptance criteria:

- [ ] <観測可能な完了条件>
- [ ] <テスト合格条件>

Context:

<scene-setting。このタスクがどこに位置するか、周辺の前提、関連既存実装>
````

## 抽出規則 (controller 側の前提)

- implementer / reviewer は、渡されたプランファイルの絶対パスに対して `grep -n '^## \|^### '` を実行し、見出し行の位置から渡されたタスク番号に一致する `### Task N:` を自分で探す
- タスク本文の範囲は、その見出し行から次の `###` または `##` 見出しの直前まで (無ければファイル末尾まで)。`Read` の `offset` / `limit` で該当範囲だけを読み、プラン全文や他タスクの本文は読まない
- `Context` はタスク本文の範囲に含まれるので別途渡さない。`対象ファイル` だけは編集してよい範囲の宣言として controller が値として直接渡す

## `## 実装タスク` セクションがないプラン

write-plan が生成する実行対象のプランは、合意事項あり・なしとも `## 実装タスク` を持つ (`../SKILL.md` の「プランの構成」)。したがってこのセクションが無いのは、write-plan が plan mode 用に書く参照スタブ (冒頭のマーカーで本体プランへ読み替えられるのでそもそも実行対象ではない) か、手書きなど write-plan 以外の経路で作られたプランに限られる。その場合 `/execute-plan` は起動時に `AskUserQuestion` で「実装タスクを追記してから再実行する」「見出し / 番号付きリストから抽出を試みる」「中止」へ誘導する。
