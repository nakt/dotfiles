# プランのワークフロー

## レビュー手順

1. プランを作成したら plan-reviewer サブエージェントを呼び出す。プランのパスと作成中に読んだ主要関連ファイルのパス一覧を渡し、結論・経緯は渡さない。
2. 結果をユーザーに確認する（原則 AskUserQuestion 1 回。4 問を超える場合は重要度順に分割）。
3. 確定事項をプランに反映して実装開始。ユーザー確認で棄却された選択肢は台帳（`issue-tracker` スキル）に 1 行記録する（プラン・ADR には書かない）。再レビューはユーザーが明示的に求めたときのみ行う。

憲章の正典は plan-reviewer 定義（`~/.claude/agents/plan-reviewer.md`）に置く。形式・体裁への指摘はしない。

## プランファイルの運用

- plan mode 中は plan mode が指定するファイルを唯一のプランファイルとする。確定済みプランがある状態で plan mode に入ったら、冒頭の固定マーカー「このファイルは参照スタブ。実行対象: <本体プランのパス>」と要約数行だけの参照スタブを書いて承認に進む。スタブに `## 実装タスク` 見出しは置かない。承認後・実装開始前にスタブを削除し、本体プランのパスを明示して実装を始める。実害: 同セッションで確定済みプランを plan mode 用に 5.7 分かけて再生成した。

## プランの構成

以下の 3 セクションのみ。この順序・見出し名で置く。

### ## 要約（必須）

5〜10 行で「何を・なぜ・どう変えるか」。略語・コードネーム・内部名称を使わない。ここだけ読めば承認判断ができることが基準。

### ## 合意事項（確定した判断があるとき必須）

A1, A2… と番号付きで、1 判断につき「判断 1〜2 行 + 根拠 1 行」。根拠には、その判断を選ばせた制約（既存資産・データ量・運用体制・非機能要件など）を書く。AskUserQuestion で確定した判断も、代替案比較で選んだ判断も、すべてここに一元化する（他の場所に判断を書かない）。棄却案・代替案の比較はプランに書かない（棄却された選択肢は台帳に 1 行記録する）。

execute-plan の controller はこのセクションを implementer / reviewer prompt に転記する。ここに無い判断は実装に引き渡されない。

### ## 実装タスク

実装者向けの本文。

## スコープの規律

- 今回の変更と同じ PR でレビューできるものは、見つけた時点でプランに含めて直す。先送りするのは、別の設計判断が要るものか、別のレビュー単位になるものだけで、それは台帳（`issue-tracker` スキル）に 1 行記録する。設計・分解は着手が決まったときに初めて行う。issue に着手して閉じるときも同じ判定を使う。実害: 2 週間で issue の起票とクローズが 18 コミットを占め、閉じる操作が次の issue を生む形が定着した。
- 積み残しの解消をプランの完了条件にしない。「台帳に記録した」で完了とする。
- 台帳のトリアージ基準: 次の 2〜3 機能の実装中に実害が出るか。出ないなら 1 行のまま放置してよい。
- レビューの指摘は、反映する前に要約を書き直して確かめる。要約が 5〜10 行に収まらなくなる、あるいは失敗経路や条件分岐の説明が要るようになったら反映せず、指摘が集中した決定のほうを落とす。落とした指摘は、台帳のトリアージ基準を満たすものだけ 1 行記録する。実害: 指摘を順に取り込み、要約を書き直さないまま変更範囲が 2 ファイル 4 箇所から 6 箇所に膨れ、ユーザーの介入で差し戻した。

## ルールの追加

このワークフローにルールを足すときは、動機となった実害（何が起きたか）を 1 行添える。日付は git 履歴に残るので本文には書かない。実害のない予防的ルールは足さない。
