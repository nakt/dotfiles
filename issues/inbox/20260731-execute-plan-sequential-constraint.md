## TL;DR

`execute-plan/SKILL.md` は implementer / reviewer subagent を同時に複数起動しないと定めるが、これはレビュー・コミットが共にパス限定で動く前提を踏まえていない。対象ファイルが互いに素なタスクなら同一ツリーでも分離は保てる。今回の棚卸しプランでは 12 タスク中 7 件が対象ファイル無交差かつ依存なしで、実際に並列実行しても問題なく完走した。

## 背景 / 問い

`execute-plan/SKILL.md` の Phase 3 冒頭の現行記述（実測）: 「タスクを 1 件ずつ逐次に処理する。implementer / reviewer subagent を同時に複数起動しない (共有ツリーで変更が混ざり、レビュー差分とコミット単位が分離できなくなるため)。」。しかし本タスク（Task 12）を含む今回の棚卸しプランでは、対象ファイルの交差が無いタスク群を並列に実行する運用が実際に行われた。

## 調査結果

- 現行の逐次制約の理由: 「共有ツリーで変更が混ざり、レビュー差分とコミット単位が分離できなくなるため」
- 実態: レビューは `git diff [BASE_SHA] -- [TARGET_FILES]` でパス限定、コミットも `git add <対象ファイル>` でパス限定して行われており、対象ファイルが互いに素なタスクであれば、同一ツリーで複数 subagent が並行して動いてもレビュー差分・コミット単位は分離できる
- 今回の棚卸しプラン（12 タスク）では、Task 1 / 2 / 5 / 6 / 8 / 9 / 10 の 7 件が対象ファイル無交差かつタスク間依存なしと判定され、並列実行された。7 件とも実装 → レビュー → コミットまで完走し、revert は発生していない
- `git log --format='%h %ad %s' --date=iso` で確認したコミットタイムスタンプが並列バッチのパターンを示している。例えば `14bfdc9`（21:47:40）と `f2b1cd3`（21:47:41）は 1 秒差、`7e39a04` と `bb45450` は両方とも 21:50:45 の同一秒で連続コミットされている
- 本 issue の起票元である Task 12 自体も、他タスクと `.claude/` 配下 vs `issues/inbox/` 配下で対象ファイルが分離された並列実行の一例

## 結論 / プラン

- [ ] 「対象ファイルが互いに素」の判定を誰がどの時点で行うかを決めた上で、逐次制約の緩和可否を検討する

## 未解決の論点 / リスク

- 「対象ファイルが互いに素」の判定を誰が（プランナーか、実行時の execute-plan か）どの時点で行うかの設計が要る
- 対象ファイルの交差判定を誤ると、レビュー差分・コミット単位の分離という当初の制約の目的が崩れる。判定ロジックの厳密さが緩和の前提になる
- 並列実行時のログ・報告フォーマットが逐次前提のままだと、どのタスクがどの subagent によるものか追いにくくなる可能性がある
