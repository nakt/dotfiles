## TL;DR

plan mode で監査を実施すると、レポート全文が呼び出し元の context に流入し(15,605 字)、承認後の保存時に同じ内容を書き写す(出力 10,818 トークン)。plan-audit SKILL が定める「呼び出し元にレポート全文は返さない」という原則とも矛盾している。削減する方法はあるが、付随して増える規定が多いため着手していない。

## 背景 / 問い

plan-audit SKILL.md 103 行目は「書き込みできない状況(plan モード・チャット環境)ではレポート全文を会話で返し、呼び出し元が承認後にファイル化する」と定める。一方 23 行目は「呼び出し元への返答は判定・要旨・レポートパスのみとし、レポート全文は返さない」と定めており、plan mode のときだけ例外が生じている。

2026-07-29 の計測(swc-voc-analyzer-v3 セッション b36b1451)で、この経路の実コストが判明した。

## 調査結果

- 監査サブエージェントの返答は attachment として 15,605 字が呼び出し元に流入した
- 承認後、呼び出し元が同じ内容を `.workspace/audits/` へ書き出し、出力 10,818 トークンを消費した
- 監査サブエージェント自身は Write を一度も使っていない(plan mode の制約指示を受けているため)

削減案とその代償(2026-07-29 のプラン elegant-waddling-cerf で検討し、着手しないと決めた):

- 承認後に呼び出し元が SendMessage で監査サブエージェントに保存を指示する。SendMessage による再開自体は本環境で動作を確認済み(context を保持したまま再開する)
- ただし付随して次が必要になる。(1) 承認をまたいで auditor を名指しするための命名規則、(2) 再開したサブエージェントが plan mode の制約指示を transcript に持ち続けて書き込みを拒否する経路の検知(SendMessage は成功して応答が返るため、失敗として観測されない)、(3) 棄却案追記の主体変更(呼び出し元が Edit するには全文の Read が必要になり、削減分が戻る)、(4) チャット環境の分岐維持
- 削減額は 1 回のプラン策定あたり出力 10.8k トークン。上記 4 点の規定をワークフロー定義に持ち込む対価としては見合わないと判断した

## 結論 / プラン

- [ ] 実害(triage 基準: 次の 2〜3 回のプラン策定で問題が出るか)が出るまで放置してよい。着手するなら、まず「plan mode 中に起動したサブエージェントが、承認後の再開時に Write を実行できるか」の 1 点を確かめる

## 未解決の論点 / リスク

- 上記の検証は plan mode 内では実行できない。承認後に監査サブエージェントへ保存を指示してみる形でしか確かめられない
